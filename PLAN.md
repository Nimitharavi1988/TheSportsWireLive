- **Real, non-obvious bug found via careful bisection** (not a version-mismatch issue): passing a JSX element directly as a prop *value* — `<Stack divider={<Divider />}>` — throws "Element type is invalid" specifically under Next.js 16 + Turbopack when rendered in a Server Component. ### Debugging note: browser-automation click reliability
Hit real flakiness testing the highlight feature that's worth recording for future sessions: `find`/`read_page` refs and their cached pixel coordinates can go stale between calls (e.g. after a navigation or reflow) and a click on a stale ref silently does nothing (no POST) or, worse, resolves to the *wrong* element from a previous page state. Symptoms: a click reports success but no network request follows, or a request fires against an unexpected article id. Fix that worked reliably: re-run `read_page` (or `find`) immediately before the click (not reusing refs across navigations), and when in doubt, cross-check the click coordinate against a fresh `screenshot` rather than trusting a stale ref's cached coordinate. `read_network_requests` remains the reliable way to confirm whether a server action actually fired — don't trust console/preview_logs alone, since both can show long-stale buffered output that looks alarming but predates the current code by hours.

### Real athlete photos via Wikimedia Commons (2026-09-06)
- User asked about free options beyond Pexels for real (not generic-stock) person photos. Wikimedia Commons is the one viable free option — Wikipedia's own non-free-content policy requires any image on a living person's page to be freely licensed, so anything sitting in an athlete's infobox is guaranteed usable. Unsplash/Shutterstock/iStock/Adobe Stock were all considered and ruled out (Unsplash is free but same generic-stock category as Pexels with no real athlete coverage; Shutterstock/iStock/Adobe Stock have real editorial photography but are paid, which is the Getty/AP-style licensing already deliberately deferred until there's revenue).
- Licensing approach: only `Public Domain`, `CC0`, `CC-BY`, `CC-BY-SA` are accepted (verified via Commons' own `extmetadata.LicenseShortName`/`License` fields); anything else is skipped, no image shown. Attribution is always displayed for CC-BY/CC-BY-SA (photographer name + license + link to the Commons file page), reusing the existing `heroImageCredit`/`heroImageCreditUrl` fields — no schema change needed. Right-of-publicity (using a real person's likeness) is covered by the well-established news/editorial-reporting exception, which is exactly our use case; not legal advice, just the practical read.
- New module: `src/lib/ingestion/wikimediaImages.ts` — `fetchPersonPhoto(name)` resolves the name to a Wikipedia article via search, gets that article's main image, then verifies the specific file's license on Commons before returning it.
- `src/lib/ingestion/commentary.ts` — the existing Gemini commentary call (per user's choice, over a regex heuristic which would miss headlines where the subject isn't named first) now also extracts the primary named person the story is about, via Gemini structured JSON output (`responseSchema`) in the same call — no extra API cost. Returns `{ commentary, personName }`.
- `src/lib/ingestion/runIngest.ts` wires it together: RSS articles with a source snippet get commentary + person-name extraction (still capped at `MAX_COMMENTARY_PER_RUN`); if a person is named, `fetchPersonPhoto` is tried first, falling back to the existing generic category stock photo (Pexels) if no free-licensed match is found.
- Verified end-to-end with a live Gemini call: "Ben Stokes will head to Australia for Big Bash cash..." correctly extracted `personName: "Ben Stokes"`, and the Wikimedia lookup returned his real (public domain) photo with proper credit.
