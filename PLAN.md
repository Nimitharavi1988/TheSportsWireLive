### Fixed: portrait photo crop cutting off faces (2026-09-06)

### Fixed: portrait photo crop cutting off faces (2026-09-06)
- User reported the Messi test article's photo showed only "neck and down," not the face. Real bug, not a data issue: every `heroImageUrl` display (`objectFit: "cover"`) had no `objectPosition` set, which defaults to centering the crop vertically. The Wikimedia headshot in question is a tall portrait source (3333×5000), and centering a vertical crop on a tall portrait cuts well below the face — confirmed via `getBoundingClientRect`/`naturalWidth`/`naturalHeight` on the live DOM.
- Fixed by adding `objectPosition: "top"` to all four `heroImageUrl` crop sites (article hero, homepage hero, "Match Results" cards, "More Headlines" strip) — biases the crop toward the top of the frame, which is correct for both headshot-style person photos and most stock/stadium photography (subject rarely sits at the very bottom edge).
- Verified on the live Messi article page — full face now visible, not just chin/kit detail.
- Follow-up: `objectPosition: "top"` alone still cut off the chin — the real issue was that the box itself wasn't tall enough to span the source photo's full face-to-chin range, so no amount of repositioning could show both forehead and chin at once (a taller crop window was the only real fix, not a different position value). Increased the article hero from `maxHeight: 360` to `460`, and the homepage hero from `height: 320` to `420`. Left the small card-grid thumbnails (110px/160px) as-is with just the position fix — a full face won't fit in a thumbnail that size regardless, same tradeoff any news site makes for small headline thumbnails. Re-verified: full forehead-to-chin now visible.

### Next.js 16 / React 19 / MUI 9 upgrade (2026-09-06)
- User asked to fix the CVEs an `npm audit` surfaced against the pinned Next.js 14.2.35 (DoS via Server Components, cache poisoning, request smuggling, SSRF in Server Actions, and more). Upgraded next→16.3.4, react/react-dom→19.2.8, @mui/material/@mui/material-nextjs/@mui/icons-material→9.4.0. `npm audit` now reports 0 vulnerabilities.
- Used the official tooling rather than hand-editing: `npx @next/codemod@canary upgrade latest` + `next-async-request-api` codemod for the async `cookies()`/`params`/`searchParams` migration (a real breaking change in 15+ — this app has many dynamic routes/search-param-reading pages that all needed updating), and `npx @mui/codemod@latest v9.0.0/system-props` for MUI v9's removal of Stack/Typography system props (alignItems, direction, spacing, fontWeight, color, display, gutterBottom, etc. all had to move into `sx`).
- Manual fixes the codemods didn't cover: `ThemeRegistry.tsx`'s `AppRouterCacheProvider` import path (`v14-appRouter` → `v16-appRouter`, matching MUI's per-Next-version export paths), `opengraph-image.tsx`'s `params` (also became async, a separate Next 16 change from the page-level one), `auth.ts`'s `clearSession()` (had to become async since it wasn't already, unlike `createSession`/`getSession`), and stripping a codemod artifact (`export const instant = false`) that isn't a real, recognized config option in the stable 16.3.4 release (the codemod runs from a canary channel ahead of stable).
- **Real, non-obvious bug found via careful bisection** (not a version-mismatch issue): passing a JSX element directly as a prop *value* — `<Stack divider={<Divider />}>` — throws "Element type is invalid" specifically under Next.js 16 + Turbopack when rendered in a Server Component. Confirmed precisely via a minimal reproduction and section-by-section bisection of the homepage (this took a lot of back-and-forth chasing red herrings — Table and Card components looked implicated at first via stale-cache-contaminated tests, but a clean re-test with `rm -rf .next` between every check showed they were both fine; the real trigger is specifically a JSX element passed as a plain prop, not as `children`). Fixed all three occurrences (homepage sidebar, article related-articles, admin flagged list) by manually interspersing `<Divider />` between mapped items instead of using the `divider` prop.
- **Debugging lesson for future sessions**: Next.js 16's Turbopack has aggressive filesystem caching enabled by default for both `next dev` and `next build`, and it produced multiple false leads during this debugging session — an edit's effect wouldn't show up until a full `rm -rf .next` + dev server restart, and even browser-side `read_console_messages`/`preview_logs` can echo stale entries (same digest/hash) across what looks like a fresh navigation. When chasing a hard-to-reproduce error post-upgrade, always fully clear `.next` and restart before trusting a "still broken" or "now fixed" result.
- Verified clean (0 console errors, correct content) on every route after the fix: homepage, article detail, admin queue, admin login, `/standings` index, `/standings/PD` detail, `/privacy`, `/terms`, and a 404. Full Vitest suite (31 tests) still passing.

### Deployment prep for Netlify (2026-09-07)
- User purchased `sportswirelive.com` (registered at Cloudflare) and asked to move deployment forward. Compared hosting options with real, verified pricing/terms rather than assumption: Vercel's free Hobby tier explicitly prohibits commercial use (would need the $20/mo Pro plan for a business site like this); Netlify's free tier explicitly permits commercial use and has mature, official Next.js support (Server Actions, ISR); Cloudflare Pages is also free + commercial-friendly with a real performance edge (sub-5ms cold starts vs. Netlify's Lambda-based 150-400ms+), but would require real migration work first (OpenNext adapter, swapping Prisma to Neon's HTTP driver adapter since Cloudflare Workers can't hold a raw TCP DB connection) — estimated 4-8 hours with real risk of surprises, given this stack has never run on Workers before. Decision: **start with Netlify now** (zero migration work, deploys as-is), revisit Cloudflare Pages later as a deliberate performance upgrade once there's real traffic — confirmed this is not a one-way door, since hosting choice doesn't affect the codebase or the (already-external) Neon database either way.
- Found and fixed two real pre-deployment gaps before connecting Netlify, not just decided-not-to-do items:
  1. **Prisma query-engine binary mismatch** — schema.prisma had no `binaryTargets` set, so the client only had the Windows dev-machine binary. Netlify Functions run on AWS Lambda underneath (RHEL-family), which needs a different engine binary — without this fix the site would build fine but crash on every database query in production, a well-documented common failure for this exact stack (Prisma + Next.js + Netlify). Added `binaryTargets = ["native", "rhel-openssl-3.0.x"]`, regenerated the client, verified no errors.
  2. **No `netlify.toml`** — added one: build command runs `prisma generate` explicitly (rather than relying on postinstall behavior), pins `NODE_VERSION = "24"` (matches local dev exactly — confirmed Netlify's own default is now also Node 24 as of July 2026), and explicitly declares the `@netlify/plugin-nextjs` build plugin.
- **Ingestion cron**: rather than a Netlify-specific Scheduled Function (which would create new platform lock-in, contradicting the "no lock-in" reasoning above), added `.github/workflows/ingest-cron.yml` — a GitHub Actions workflow (repo already exists: `github.com/Nimitharavi1988/TheSportsWireLive`) that calls the existing `/api/cron/ingest` endpoint every 15 minutes via a plain HTTPS request, same as the README's original cPanel-cron suggestion but host-agnostic. Requires two GitHub repo secrets to be set (`CRON_SECRET`, `SITE_URL`) — not yet done, user's own action (repo settings access).

### Debugging note: browser-automation click reliability
Hit real flakiness testing the highlight feature that's worth recording for future sessions: `find`/`read_page` refs and their cached pixel coordinates can go stale between calls (e.g. after a navigation or reflow) and a click on a stale ref silently does nothing (no POST) or, worse, resolves to the *wrong* element from a previous page state. Symptoms: a click reports success but no network request follows, or a request fires against an unexpected article id. Fix that worked reliably: re-run `read_page` (or `find`) immediately before the click (not reusing refs across navigations), and when in doubt, cross-check the click coordinate against a fresh `screenshot` rather than trusting a stale ref's cached coordinate. `read_network_requests` remains the reliable way to confirm whether a server action actually fired — don't trust console/preview_logs alone, since both can show long-stale buffered output that looks alarming but predates the current code by hours.
